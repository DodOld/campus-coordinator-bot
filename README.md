# campus-coordinator-bot

# Это ветка master

Асинхронный Telegram-бот для групповых мероприятий. Он работает только в
разрешённых группах, поддерживает forum topics, уведомления `!all`, мониторинг
публичных VK-сообществ через официальный API и изолированный фундамент для
iCalendar.

## Возможности и границы

- Личные сообщения, неразрешённые группы и неподходящие темы не получают ответа.
- Бот отправляет сообщения только в настроенные темы `Debug`, `Posts` и
  `Schedule` конкретной группы. Ошибки, результаты фоновых задач и настройка
  источников идут исключительно в `Debug`.
- `!help` доступна любому участнику разрешённой группы в теме `Debug` и выводит
  справку по всем командам.
- `!all` можно написать в любой теме разрешённой группы. Бот не отвечает в этой
  теме: сначала отправляет упоминания в `Debug`, затем сообщение
  `Вас упомянули в «ссылка»`. Слово «ссылка» ведёт к исходному сообщению.
- Telegram Bot API **не умеет перечислять всех участников группы**. Поэтому
  `MEMBER_IDS_JSON` содержит предоставленный оператором roster. Перед каждой
  отправкой бот проверяет каждый ID через `getChatMember` и исключает ботов,
  удалённых/покинувших пользователей. Если Bot API не может построить безопасную
  ссылку (например, для legacy basic group), упоминания не отправляются.
- Мониторинг VK использует только `wall.get`, не скрейпит сайт, не использует
  пользовательские логины и не копирует вложения или полный текст. База данных
  дедуплицирует `(источник, ID поста)` до попытки доставки: после рестарта пост
  не дублируется. При неоднозначной ошибке доставки возможна пропущенная, но не
  повторённая публикация — это сознательный at-most-once компромисс.

## Быстрый запуск

Нужны Docker Compose и созданный у [@BotFather](https://t.me/BotFather) токен.

```sh
cp .env.example .env
# отредактируйте .env: токены, пароль Postgres, chat ID, topic ID и roster
docker compose up --build
```

Контейнер запускает `alembic upgrade head` перед ботом. Проверка состояния:

```sh
curl http://localhost:8080/healthz
```

Для локального запуска без Docker установите зависимости (например, `uv sync`),
запустите PostgreSQL, затем:

```sh
alembic upgrade head
uv run campus-coordinator-bot
```

## Настройка `.env`

`.env` — секретный файл: он исключён из Git. Не отправляйте его в issue, чат или
репозиторий. В production предпочтительнее Docker Secrets/secret manager,
которые передают значения в переменные окружения.

```dotenv
TELEGRAM_BOT_TOKEN=...
VK_API_TOKEN=...
POSTGRES_PASSWORD=use-a-long-random-password
DATABASE_URL=postgresql+asyncpg://campus_bot:use-a-long-random-password@db:5432/campus_bot
ALLOWED_CHAT_IDS=-1001234567890
TOPIC_POLICY_JSON={"-1001234567890":{"debug":101,"posts":102,"schedule":103}}
MEMBER_IDS_JSON=[111111111,222222222]
GO_SCHEDULE_BINARY=/usr/local/bin/schedule-bot
GO_SCHEDULE_TIMEOUT_SECONDS=60
```

`TOPIC_POLICY_JSON` задаётся отдельно для каждого `chat_id`. В forum-группе
`debug`, `posts` и `schedule` — это `message_thread_id` соответствующих тем.
Создайте их в Telegram, откройте тему и получите ID из лога тестового апдейта
либо используйте известный вашему администратору инструмент для просмотра
`message_thread_id`; в production не помещайте полные апдейты с персональными
данными в публичные логи.

Для группы без тем установите `debug: null`; Debug-уведомления тогда идут в
корень группы. `posts` и `schedule` в такой конфигурации пока не поддерживают
VK-цели, так как у них нет topic ID. Если Debug не настроен/недоступен, бот
оставляет санитарное структурированное сообщение только в stdout.

## Telegram-права и `!all`

Добавьте бота в разрешённую супергруппу и выдайте ему право писать сообщения.
Для `!vk` он дополнительно проверяет, что вызывающий пользователь — администратор
группы. Сам бот не создаёт и не редактирует темы, поэтому право управления
темами ему не требуется. Отключите Privacy Mode у BotFather, иначе Telegram
может не присылать текстовые команды с префиксом `!` из группы.

`!all` доступна всем пользователям разрешённой группы. В теме `Debug` любой
участник также может вызвать `!help` и запросить расписание. Примеры:

```text
!help
!all
!all Встреча начнётся через 10 минут
!help
!schedule
!schedule mon
```

Команда не пересылает исходное сообщение и не показывает его raw URL. Участник
может открыть оригинал по форматированной ссылке при наличии доступа к группе.
Защищённый контент и ограничения Telegram-клиента могут препятствовать переходу;
бот запишет аудит и отправит нейтральное сообщение в Debug без секретов.

## VK-источники

Получите service/access token VK с минимально необходимым доступом к чтению
публичной стены и внесите его в `VK_API_TOKEN`. Администратор разрешённой группы
выполняет команды только в теме `Debug`:

```text
!vk add https://vk.ru/example 102
!vk add example 102 preview
!vk list
!vk remove 1
```

Целевой ID обязан совпадать с настроенной темой `Posts` или `Schedule`; иные
темы отклоняются. При добавлении бот запоминает текущие собственные публикации
сообщества и не высылает историю. В ответе VK API иногда встречаются сторонние
записи на стене; бот игнорирует их и никогда не использует их ID как курсор.
Далее новые посты доставляются с названием сообщества, коротким безопасным
фрагментом только при `preview` и ссылкой на оригинал. Временные
ошибки/лимиты VK повторяются с экспоненциальной задержкой; окончательная ошибка
отправляется в Debug в санитарном виде.

Для сообществ, которыми владеют ваши администраторы, отдельно можно спроектировать
VK Community Long Poll или Callback API: потребуется подтверждение владения,
callback URL, секрет верификации и обработка повторной доставки. Это не является
способом мгновенно отслеживать чужие публичные сообщества и не включено в этот
релиз.

## Расписание 0B62

Сейчас расписание временно настроено только для группы **0B62**. Его получает
включённый в образ Go-парсер: при каждом запросе он скачивает актуальный ICS из
источника ТПУ, разбирает выбранную дату и возвращает Python-боту только готовый
текст. В теме `Schedule` бот показывает его в моноширинном MarkdownV2-блоке,
сохраняя переносы строк. ICS сохраняется лишь во временный файл на время
обработки; бинарник и выгрузки не хранятся в репозитории.

Команды доступны только в теме `Debug` и любому участнику разрешённой группы:

```text
!schedule
!schedule mon|tue|wed|thu|fri|sat
```

Первая команда публикует расписание на сегодня, вторая — на ближайший указанный
день недели. `sun` намеренно не поддерживается. В `Debug` бот сообщает только о
старте, результате или безопасной ошибке; собственно расписание приходит только
в тему `Schedule`. Каждый день в **00:00 по томскому времени (Asia/Tomsk,
UTC+7)** бот публикует расписание на этот день. Таблица БД не позволяет
повторно публиковать уже успешно доставленный ежедневный выпуск после рестарта.

`GO_SCHEDULE_BINARY` указывает путь к Go-бинарнику; в Docker он собирается
многоступенчатой сборкой и по умолчанию находится в
`/usr/local/bin/schedule-bot`. `GO_SCHEDULE_TIMEOUT_SECONDS` ограничивает время
его работы. Если источник ТПУ изменит внутреннюю форму, URL или идентификатор
календаря, бот сообщит об ошибке в `Debug`, а Go-парсер потребуется обновить.
Получение произвольной группы по ID из ссылки вида
`https://my-rasp.tpu.ru/gruppa_45187/...` пока не реализовано: для него нужна
документированная схема соответствия публичного ID внутреннему календарю ТПУ.

`app.schedule` по-прежнему содержит независимые `ScheduleProvider` и
`ICalendarScheduleProvider` для локальных или HTTP(S) `.ics`, нормализации
часовых поясов, recurrence и выборок «сегодня/завтра». Контракт будущей замены
временного Go-источника зафиксирован в TODO модуля: аутентификация, модель
событий, часовой пояс, повторы/исключения/отмены, sync cursor, идемпотентность,
ошибки, лимиты и SLA.

## Разработка и тесты

```sh
uv sync --all-groups
uv run ruff check .
uv run pytest
```

Тесты проверяют пачкование mention entities, игнорирование private chat,
дедупликацию VK-постов и retry/rate-limit обработку. Логи — JSON в stdout; токены,
пароли, ключи и заголовки авторизации маскируются.
